# Horde Service_Twitter — V2 API client

This library ships two coexisting API clients:

- `Horde\Service\Twitter\V1\` — OAuth 1.0a + REST v1.1 endpoints (legacy)
- `Horde\Service\Twitter\V2\` — OAuth 2.0 + REST v2 endpoints

The two are independent. Pick the one whose endpoints your application
actually needs; nothing forces you to use both.

## Quick start

```php
use Horde\Service\Twitter\V2\TwitterApiClient;
use Horde\Service\Twitter\V2\CreateTweetParams;
use Horde\Service\Twitter\V2\TweetFieldsParams;

// Bring your own PSR-18 client + PSR-17 factories. The HTTP client must
// inject Authorization: Bearer <user-access-token> for the OAuth2 scopes
// your call requires. Horde/OAuth's AuthenticatedHttpClient wraps a PSR-18
// client with that behaviour automatically and handles 401 refresh.
$client = TwitterApiClient::create(
    httpClient: $authenticatedHttpClient,
    requestFactory: $psr17RequestFactory,
    streamFactory: $psr17StreamFactory,
);

$me = $client->getMe();

$tweet = $client->createTweet(new CreateTweetParams(text: 'Hello v2'));

$timeline = $client->getUserTimeline(
    userId: $me->id,
    fields: new TweetFieldsParams(
        tweetFields: ['created_at', 'public_metrics', 'entities', 'attachments'],
        expansions: ['attachments.media_keys', 'author_id'],
        mediaFields: ['url', 'preview_image_url', 'alt_text'],
    ),
);
foreach ($timeline->iterator() as $tweet) {
    // iterator() auto-paginates until Twitter stops returning next_token
}
```

## Supported endpoints

| Method | HTTP route | Required scope |
|---|---|---|
| `getMe()` | `GET /2/users/me` | `users.read tweet.read` |
| `getTweet($id)` | `GET /2/tweets/{id}` | `tweet.read users.read` |
| `createTweet(CreateTweetParams)` | `POST /2/tweets` | `tweet.write users.read tweet.read` |
| `deleteTweet($id)` | `DELETE /2/tweets/{id}` | `tweet.write` |
| `getUserTimeline($userId, ...)` | `GET /2/users/{id}/tweets` | `tweet.read users.read` |
| `retweet($userId, $tweetId)` | `POST /2/users/{id}/retweets` | `tweet.write users.read tweet.read` |
| `undoRetweet($userId, $tweetId)` | `DELETE /2/users/{id}/retweets/{tweet_id}` | `tweet.write` |
| `likeTweet($userId, $tweetId)` | `POST /2/users/{id}/likes` | `like.write users.read tweet.read` |
| `unlikeTweet($userId, $tweetId)` | `DELETE /2/users/{id}/likes/{tweet_id}` | `like.write` |
| `getBookmarks($userId, ...)` | `GET /2/users/{id}/bookmarks` | `bookmark.read tweet.read users.read` |
| `addBookmark($userId, $tweetId)` | `POST /2/users/{id}/bookmarks` | `bookmark.write` |

All of these accept `OAuth 2.0 user-context` tokens. Endpoints marked
`tweet.read` / `users.read` alone also accept `OAuth 2.0 app-only` Bearer
tokens for fully public reads, though that is the caller's responsibility:
the client treats authentication as opaque PSR-18 plumbing and does not
distinguish modes internally.

## Field selection and expansions

`TweetFieldsParams` controls everything Twitter ships beyond the bare
required fields:

```php
new TweetFieldsParams(
    tweetFields: ['created_at', 'public_metrics', 'entities', 'attachments',
                  'context_annotations', 'reply_settings', 'geo'],
    userFields:  ['profile_image_url', 'description', 'verified'],
    mediaFields: ['url', 'preview_image_url', 'alt_text', 'duration_ms'],
    pollFields:  ['options', 'voting_status', 'end_datetime'],
    placeFields: ['full_name', 'country', 'country_code'],
    expansions:  ['author_id', 'attachments.media_keys',
                  'attachments.poll_ids', 'geo.place_id',
                  'referenced_tweets.id'],
)
```

When `expansions` is set, Twitter returns side-channel `includes` objects.
Paginated responses surface those via `$response->includes`, an `Includes`
bag with `user($id)`, `tweet($id)`, `mediaByKey($key)`, `poll($id)`,
`place($id)` lookups. Single-resource calls (`getMe`, `getTweet`,
`createTweet`) currently return only the parsed `User` / `Tweet`; their
`includes` block is not surfaced. Request expansions you actually need on a
paginated route, or upgrade to a custom call if you need expansions on a
single-resource fetch — that affordance is a future addition.

## Pagination

`getUserTimeline` and `getBookmarks` return `PaginatedResponse<Tweet>`. Three
walk modes are supported:

```php
// One page at a time
$page = $client->getUserTimeline($userId);
foreach ($page->data as $tweet) { ... }
if ($page->meta->hasNextPage()) {
    $next = $client->getUserTimeline(
        $userId,
        new UserTimelineParams(paginationToken: $page->meta->nextToken),
    );
}

// All pages, lazily — iterator() fetches the next page only when the
// current page is exhausted. Stops as soon as Twitter omits next_token.
foreach ($page->iterator() as $tweet) { ... }
```

## Rate limiting

Every 429 response becomes a `RateLimitException` (a subclass of
`TwitterApiException`, so existing catch-all error handling keeps working):

```php
try {
    $client->createTweet($params);
} catch (\Horde\Service\Twitter\V2\RateLimitException $e) {
    // $e->limit, $e->remaining are ints (null if header was missing)
    // $e->resetAt is a DateTimeImmutable (null if header was missing)
    // $e->retryAfter is the Retry-After value in seconds (null if missing)
}
```

## Media uploads

Twitter v2 still routes media upload through the **v1.1**
`POST /1.1/media/upload.json` endpoint (chunked: INIT → APPEND → FINALIZE →
optional STATUS). That endpoint is **not part of this library yet**; it
needs an OAuth 1.0a or OAuth 2.0 user-context credential and a different
request shape from the rest of v2.

The shippable pattern today: upload through whatever v1.1-compatible client
you already have, take the resulting media id, and pass it to
`CreateTweetParams::mediaIds`:

```php
$mediaId = $myV1Uploader->upload('/path/to/photo.jpg'); // returns "3_..."
$client->createTweet(new CreateTweetParams(
    text: 'Photo tweet',
    mediaIds: [$mediaId],
));
```

A first-class chunked uploader on top of v1.1 is on the 3.1 roadmap.

## Deferred — not in this release

The following Twitter v2 API surfaces are intentionally **not** implemented;
they are large enough to warrant separate releases and are tracked
separately:

- **Streaming** — filtered stream, sampled stream, volume stream (long-lived
  HTTP connections, rule management). No support.
- **Lists** — `GET/POST /2/lists/*`, members, follows. No support.
- **DMs** — `GET /2/dm_conversations/*`, `GET /2/dm_events`, send DM. No
  support.
- **Spaces** — `GET /2/spaces/*` (live audio). No support.
- **Compliance** — `POST /2/compliance/jobs`. No support.
- **Search** — `GET /2/tweets/search/recent`, `…/all`. No support.
- **Reverse-lookup endpoints** — `GET /2/tweets/{id}/liking_users`,
  `…/retweeted_by`, `…/quote_tweets`. No support.

If your application needs one of these surfaces today, build it directly
against the PSR-18 client you already inject into `TwitterApiClient` — the
auth plumbing carries over.

## V1 → V2 upgrade notes

The V1 client (`Horde\Service\Twitter\V1\`) targets OAuth 1.0a and v1.1 REST
endpoints. Twitter has deprecated v1.1 for most non-media operations.
Existing code calling `Horde_Service_Twitter` (legacy `lib/`, PSR-0) or
`Horde\Service\Twitter\V1\TwitterApiClient` keeps working. New code should
prefer V2.

There is no V1↔V2 method-by-method mapping helper; the two surfaces differ
enough (id shapes, field names, auth model) that adapter code adds more
friction than it saves. Port one endpoint at a time.
